# 端末内保存データのキー・スキーマ変更と移行

## 目的
サーバを持たない単一HTMLアプリでは端末内保存が唯一の正本である。キー変更・構造変更・リセットでデータを消失させないよう、移行前退避・正規化・読み戻し照合・復元導線を必ず通す。

## 発動条件
- 保存キー名の変更、または新版作成時の保存キー決定
- 保存データのフィールド追加・改名・型変更・入れ子変更
- localStorage → IndexedDB 等、保存先の変更
- 初期化・リセット・全消去機能の追加や変更
- 読込時の検証失敗時の扱い（破棄・停止）を実装する

## 入力
| 項目 | 内容 |
|---|---|
| 現行キー一覧 | 対象アプリの全キーと保存例 |
| 新形式定義 | 新キー・新構造・既定値 |
| 配信オリジン | 例: `https://highlightyjp.github.io`（同一オリジンの他アプリ一覧を含む） |

## 出力
| 項目 | 内容 |
|---|---|
| キー棚卸し表 | アプリ別・キー別（同一オリジンの他アプリ分を含む） |
| 移行設計表 | 旧キー → 新キー、変換規則、不正値の扱い、未知版の扱い |
| 実装差分 | 移行処理・退避・復元・リセット |
| 検証結果 | 移行前後の件数照合、旧形式データでの起動確認、復元確認 |

## 手順
1. キー棚卸し: 対象アプリと同一オリジンの全アプリについて抽出する。
   ```bash
   grep -noE "localStorage\.(get|set|remove)Item\(['\"][^'\"]+|[A-Z_]*KEY[A-Z_]*\s*=\s*['\"][^'\"]+|indexedDB\.open\([^)]*\)|localStorage\.clear\(\)" *.html */index.html
   ```
2. キー接頭辞をアプリ固有にする（例: `mt:` `coorde:`）。他アプリと衝突しないことを棚卸し表で確認する。
3. 保存値に版を持たせる: `{ v: SCHEMA, data: ... }`。
4. 読込処理を次の分岐で実装する。
   - 版一致 → 採用
   - 旧形式（版なし等）→ 移行対象
   - 未知の版・JSONパース失敗 → そのキーの保存を停止（上書き禁止）し、画面に表示する
5. 移行前に、旧データの生文字列を退避キー（例: `<prefix>snapshot`）へ保存する。
6. 正規化関数を1つにまとめ、保存・起動・読込（インポート）・復元の全経路で同じ関数を通す。
7. 移行後に読み戻し、件数（配列長・キー数）を移行前と照合する。不一致なら復元導線付きでエラー表示する。
8. 復元: 退避キーから戻す処理を用意し、戻す前の状態も退避する。
9. リセット: アプリ接頭辞のキーのみを列挙して削除する。
10. 書き出し（バックアップ）手段が移行前から利用可能であることを確認する。
11. 検証: 旧版で作成したデータを用意し、新版で起動 → 件数照合 → 復元 → 再移行の順で確認する。

参照実装: `machiapp-techo/index.html` の `loadAll` / `normAll` / `writeSnap` / `restoreSnap` / `parseImport`。

## 注意点（やってはいけないこと）
- `localStorage.clear()` を使わない。同一オリジン（GitHub Pages では `https://highlightyjp.github.io` 配下の全リポジトリ）の他アプリのデータも消える。
- 検証失敗時にデータを即削除しない（退避・保存停止で止める）。
- `{...DEF, ...JSON.parse(saved)}` の浅いマージだけで移行済みとしない（入れ子の欠落・型不整合が残る）。
- 新版でキー名だけ変えて旧データを放置しない（利用者には「データが消えた」状態になる）。
- 認証を経ない全消去経路（特定の入力値で初期化する等）を追加しない。
- 実データで移行試験をしない。試験データは架空値で作る。
- 既存アプリの保存キー・スキーマを指示なく変更しない。
