状態: 清書（ラウンド3）。評価（試行・採点）は未実施。

旧下書き: `phase-gate-transition`（INDEX 4章の 08）、`freeze-seal-verify`（09）、`app-variant-lineage-registry`（03）。17 に対応する旧下書きは本リポジトリに無い。番号と旧下書きの対応付けは本清書の作成セッションによる評価・解釈で、本人の決定ではない。

## 目的

フェーズの進行・凍結・新版の作成を、プロジェクトごとの書式の違いに関係なく同じ手順で判定し、記録として残す。

- 各プロジェクトの規則（`CLAUDE.md`、統一指示書、`phase_gates.md` など）の本文は本スキルに写さない。本スキルが定めるのは、それらの規則を読んで判定する手順と、判定結果の記録の形だけである。
- 規則が書かれている場所はプロジェクトごとに違う（下の「プロジェクト別の所在」）。本スキルはそれをまたいで使う。

## 発動条件

- フェーズの完了を宣言しようとしている（自分が宣言する場合も、本人の宣言を記録する場合も）
- 次のフェーズを始める
- 既存アプリ・成果物の派生版や新版を作る（凍結物に変更が必要になった場合を含む）

上記以外（通常の作業中の範囲判定だけ）では発動しない。フェーズ規則そのものは各プロジェクトの規則ファイルが常時適用される。

## 手順

### A. ゲート判定（フェーズ完了の宣言時・次フェーズの開始時）

1. 規則を読む。対象プロジェクトの規則ファイルを、そのファイルが定める読込順で読む。読んだファイルのパスとコミットを記録する。本スキルの手順と規則ファイルが食い違う場合は規則ファイルに従い、食い違いを報告する。
2. 現在フェーズと、宣言しようとしているフェーズを特定する。正本ファイルがあれば値を引用し、無ければ（railway・main）「正本なし」と書き、何を根拠にフェーズを特定したか（コミット件名・本人の指示文）を書く。
3. フェーズ外の実装がないかを判定する。
   ```bash
   git diff --name-status <開始コミット>..<終了コミット>
   git log --format='%h %ad %s' --date=iso <開始コミット>..<終了コミット>
   ```
   変更されたファイルを1件ずつ、フェーズ定義の対象範囲に入るかで分ける。完了・凍結済みフェーズの成果物への変更、未着手フェーズの成果物の先行作成は「フェーズ外」として全件列挙する。判定できないファイルは「判定不能」とし、理由を書く。
4. 実データが全量かを判定する【17】。
   - 全量の定義（入力）と、成果物に含まれる件数を、コマンドで数えた値で並べる。数えたコマンドと出力を残す。
   - 件数が一致しない、または全量の定義が無い場合は「未達」または「判定不能」とし、不足をデータの欠陥として報告する。サンプル・抜粋で足りるという判断はしない。
   - 件数の一致だけで中身の正しさまでは判定しない。中身の検証は S7『データ来歴（生成と監査）』（`highlightyjp/app` の `skills-drafts/data-lineage-generation-audit/SKILL.md`。ブランチ `claude/vibrant-brown-27k6az`、未マージ。前身は `data-provenance-audit`） に渡す。
5. 規則ファイルにあるゲート条件を1件ずつ判定する。各条件に「充足／未充足／判定不能」と根拠（ファイル:行、コミット、コマンド出力）を付ける。本人の承認が必要な条件は、エージェント側で充足にしない。
6. 総合判定を出す。手順3でフェーズ外が1件でもある、手順4・5で未充足・判定不能が1件でもあれば「ゲート未達」とする。未達の条件と、充足に必要な作業（本人がすること・エージェントがすること）を分けて書く。

### B. 進行記録

7. 判定結果を記録する。記録先は規則ファイルが定める場所（sidebiz なら `execution_log.md`）。定めが無いプロジェクト（railway・main）では、記録先を本人に確認し、決まるまでは報告文だけに残す。
   - 日時はタイムゾーンを付けて書く（例: `2026-11-02T11:10:35Z` または `2026-11-02 20:10 (JST)`）。
   - 既存の記録に追記するときは、直前の記録より新しい日時であることを確かめる（INDEX 7章 D17 の時系列逆転を作らない）。
8. 正本ファイルがある場合、全条件が充足したときだけ正本を更新する。未達なら正本を変えない。

### C. 凍結物の封印（凍結するとき）

9. 作業ツリーがクリーンであることを確かめる（`git status --porcelain` の出力が空）。
10. 凍結対象の SHA-256 を全長64桁で計算し、封印したコミットと日時を記録する。
    ```bash
    sha256sum <path1> <path2> ...          # ファイル・SHA-256
    git rev-parse HEAD                      # 封印したコミット（全長）
    date -u +%Y-%m-%dT%H:%M:%SZ             # 日時（UTC）
    ```
11. 封印台帳に1行ずつ記録する（出力の「封印台帳」の形）。台帳の置き場は本人が決める（注意点 N2）。決まるまでは、凍結宣言の文書と同じコミットに含める案を示し、確定はしない。

### D. 改変の検知（次のフェーズを始めるとき。凍結物を含むブランチのマージ前にも行う）

12. 封印台帳の各ファイルの SHA-256 を再計算し、台帳の値と比べる。
    ```bash
    sha256sum -c <封印台帳を sha256sum 形式で書き出したファイル>
    # 別ブランチ上の内容と比べる場合
    git show <ブランチ>:<path> | sha256sum
    git log -1 --format='%h %ad %s' --date=iso <ブランチ> -- <path>
    git branch -r --contains <封印したコミット>
    ```
13. 台帳のハッシュが先頭8桁などに切り詰められている場合は、前方一致で照合したことと、全長での照合ができないことを結果に書く。
14. 不一致・乖離は事実だけを報告する。どちらを正とするか、解消の方法（新版にする・戻す・マージする）は本人が決める。凍結物は編集しない。

### E. 新版の作成（派生版・新版を作るとき）

15. 作り方を確定する。上書きか新しいファイルかは本人の指示に従う。凍結物は上書きしない。指示が無ければ確認する。
16. 命名する。命名規則は本人が決める事項で、まだ決まっていない（注意点 N1）。決まるまでは、本人の指定した名前を使い、指定が無ければ確認する。既存ファイルの名前は変えない。
17. 版表記をそろえる。版番号が書かれている箇所をすべて列挙し、同じ値にする。
    ```bash
    # 例: machiapp-techo
    grep -nE "<title>|APP_VERSION|VERSION\s*=" machiapp-techo/index.html machiapp-techo/sw.js
    grep -rnF '<旧版番号>' machiapp-techo/
    ```
    同梱ファイル（例: `machiapp-techo/LICENSES.txt`）も検索の対象にする。取り残しの照合の詳細は S6（`version-diff-audit`）。Service Worker の版は S14、保存キーを変える場合は S13 へ渡す。
18. 系譜を登録する。系譜台帳に1行追記する（出力の「系譜の追記」の形）。台帳が無い場合は追記せず、記録すべき内容を報告に書き、台帳の置き場を本人に確認する（注意点 N2）。親ファイルが特定できない場合、類似度などで推定した親は「評価・解釈（推定）」と明記する。
19. コミットメッセージに版番号と変更の要約を書く。Web UI の既定文言（`〇〇を更新`、`Add files via upload`）は使わない。

品質ルール:

- 確認できなかったことを「充足」「一致」にしない。根拠区分は「確認済み／評価・解釈／未確認」の3つだけを使う。本人申告は、発言があったことは確認済み、発言の中身は未確認として扱う。実測は確認済みとし、方法と日時を書く。算出値は、入力と式が確認済みのときだけ「確認済み（算出）」、未確認の入力が混ざれば「未確認（算出）」とする。この対応付けは依頼文の指定による。
- コマンドと出力を伴わない「PASS」「充足」を記録しない（INDEX 7章 D3）。
- ハッシュを先頭8桁などに切り詰めて新たに記録しない。
- 肯定のみの報告をしない。通過した場合も、判定不能だった条件と、照合できなかった範囲を書く。

してはいけないこと:

- 凍結物を1文字も編集しない（整形・改行コードの変更を含む）。照合を合わせるために台帳を書き換えない。
- ゲート条件を読み替え・緩和しない。未達のまま次のフェーズへ進めない。
- 乖離を自分の判断で解消しない（main の上書き・revert・強制 push をしない）。
- 既存ファイルの名前の変更・削除・統合を指示なく行わない。台帳ファイルを指示なく新設しない。
- `final` `perfect` `super` `FIXED` などの序列語を版番号の代わりにしない。
