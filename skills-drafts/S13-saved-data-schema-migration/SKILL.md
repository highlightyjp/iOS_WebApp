# 保存スキーマ移行（S13）

状態: 清書（ラウンド3）。評価（試行・採点）は未実施。
由来: ラウンド2の S13。統合リスト（ラウンド1）の 21。統合リストの原文は未取得（INDEX 11章）。
旧下書き: `storage-schema-migration`（INDEX 4章の 04）。番号と旧下書きの対応付けは本清書の作成セッションによる評価・解釈で、本人の決定ではない。

## 目的

サーバを持たないアプリでは、端末内の保存データが利用者の唯一の正本になる。キーや構造の変更でデータを失わないよう、移行の仕様を先に表で固定し、退避と読み戻しの照合を通してから切り替える。

## 発動条件

- localStorage のキー名、保存する値の構造（フィールドの追加・改名・型変更・入れ子の変更）を変える
- IndexedDB のデータベース名・オブジェクトストア・キー・値の構造を変える
- 保存先を変える（例: localStorage → IndexedDB。`coorde/index.html:518` のコメント「旧版のlocalStorage(coorde:*)は初回に移行」）
- 新版の作成で保存キーを決める（S12 手順E から呼ばれる）

## 入力

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 旧スキーマ | 必須 | 旧版のキー一覧と値の構造。コードから抽出する（手順1） |
| 新スキーマ | 必須 | 新しいキー・構造・既定値・版番号 |
| 既存データの例 | 必須 | 旧版で実際に保存される形のデータ。どのデータを使うかは注意点 G1 を参照 |
| 初期化の方針 | 必須 | 本人が決めた方針（初期化を許すか、許すならどの操作で、どの範囲か）。未決定なら「未決定」と書き、初期化する処理を作らない |
| 配信オリジン | 任意 | 例: `https://highlightyjp.github.io`。同じオリジンの他アプリのキーを巻き込まないかの確認に使う |

## 手順

1. 旧スキーマを抽出する。対象アプリと、同じオリジンで配信される他アプリの両方を対象にする。
   ```bash
   grep -noE "localStorage\.(get|set|remove)Item\(['\"][^'\"]+|[A-Z_]*KEY[A-Z_]*\s*=\s*['\"][^'\"]+|indexedDB\.open\([^)]*\)|createObjectStore\([^)]*\)|localStorage\.clear\(\)" *.html */index.html
   ```
   出力の全行を、アプリ・キー・操作（読む・書く・消す・全消去）に分けて表にする。

2. キーと構造の対応表を作る（出力の「対応表」）。旧キー1つずつについて、新キー、変換規則、不正な値・欠けた値の扱いを書く。新スキーマに対応する旧項目が無い項目、旧スキーマにあって新スキーマで捨てる項目は、それぞれ全件列挙する。捨てる項目は本人の承認を得るまで捨てない。

3. 移行の仕様を決める。保存値に版を持たせ（例: `{ v: SCHEMA, data: ... }`）、読込時に版で分岐する。
   | 読み込んだ値 | 扱い |
   | --- | --- |
   | 版が現行と一致 | そのまま使う。移行しない |
   | 版が無い（旧形式）、または現行より古い版 | 移行の対象 |
   | 版が現行より新しい、または未知 | そのキーへの保存を止める（上書きしない）。画面に表示する |
   | JSON として読めない | 同上。削除しない |

4. 移行関数を、何度実行しても同じ結果になる作りにする（冪等）。
   - 版が現行と一致する値には何もしない（2回目の実行で変化が起きない）。
   - 変換は旧値だけから新値を作る。現在時刻・乱数・実行回数に依存する値を作らない（必要なら移行前の値から決まる値にする）。
   - 旧キーから新キーへ移す場合、新キーへの書き込みと読み戻しの照合（手順6）が通るまで旧キーを消さない。旧キーを消すかどうかは本人の方針に従い、方針が無ければ残す。
   ```js
   // 形の例（版キーで分岐。何度呼んでも同じ結果）
   function migrate(raw) {                       // raw: 保存されていた文字列
     let p; try { p = JSON.parse(raw); } catch (e) { return { stop: "parse" }; }
     const v = (p && typeof p === "object" && !Array.isArray(p) && "v" in p) ? p.v : 0;
     if (v === SCHEMA) return { value: p };       // 移行済み: 変更しない
     if (v > SCHEMA || !STEPS[v]) return { stop: "unknown-version" };
     let cur = v === 0 ? p : p.data;
     for (let k = v; k < SCHEMA; k++) cur = STEPS[k](cur);   // 版ごとの変換を順に適用
     return { value: { v: SCHEMA, data: cur } };
   }
   ```
   参照実装: `machiapp-techo/index.html` の `loadAll`（10731行〜）、`normAll`（10684行〜）、`writeSnap`（10705行）、`restoreSnap`（11686行〜）、`parseImport`（11655行〜）。`SCHEMA = 2`（10388行）。

5. 旧データを退避する。移行の前に、旧データの生の文字列を、アプリ固有の退避キー（例: `mt:snapshot`、`machiapp-techo/index.html:10434`）に保存する。退避に失敗した場合は移行しない。退避から戻す処理を用意し、戻す前の状態も退避する。

6. 読み戻して照合する。移行後に新キーを読み戻し、移行前と件数（配列の長さ・キーの数）を比べる。一致しない場合はエラーを表示し、退避から戻す手段を示す（参照実装: `loadAll` 内の読み戻し照合）。

7. 失敗時の扱いを決める。無断で初期化しない。
   - 移行・照合・読込に失敗したら、そのキーの保存を止め、画面に表示し、退避から戻す手段と書き出し（バックアップ）の手段を示す。
   - 失敗を理由に `removeItem`・`clear()`・既定値での上書きをしない（反例: `estateos.html:349`・`:368` は検証に失敗すると `aegis_state_v21` を削除する）。
   - 初期化は、入力の「初期化の方針」で本人が許した操作と範囲でだけ行う。範囲はアプリ固有の接頭辞を持つキーに限る（`localStorage.clear()` は同じオリジンの全アプリのデータを消す。INDEX 7章 D7）。

8. 旧版データで移行テストを行う。
   1. 旧版のファイル（`git show <旧版のコミット>:<パス>`）をローカル配信し、旧版の操作で保存データを作る。または、入力の「既存データの例」を旧キーに書き込む。
   2. 新版を同じオリジン・同じブラウザプロファイルで開く。
   3. 新キーの値・件数を移行前と比べる（手順6と同じ照合）。
   4. 新版をもう一度読み込み、値が変わらないことを確かめる（冪等の確認）。
   5. 退避から戻し、旧版の状態に戻ることを確かめる。
   6. 未知の版・壊れた JSON を書き込んで起動し、保存が止まり、データが消えないことを確かめる。
   ```bash
   python3 -m http.server 8000   # 別端末で配信し、Playwright で localStorage を読み書きする
   ```
   Playwright（Chromium）での確認は、iOS Safari・ホーム画面アプリでの確認ではない。実機は未確認として扱う。

9. データが失われるリスクを書く（出力の「リスク」）。少なくとも次の各項目について、該当／非該当／判定不能を書く: 捨てる項目、型変換で精度・桁が落ちる項目、旧キーの削除、初期化の経路、同じオリジンの他アプリへの影響、Safari タブとホーム画面アプリで保存領域が別であること（`machiapp-techo` が案内を表示。INDEX 5章 05）、ブラウザによる保存データの自動削除（`navigator.storage.persist` の有無）。

| # | 旧下書き 04 | 依頼文の定義 | 本清書の扱い |
| --- | --- | --- | --- |
| G1 | 「実データで移行試験をしない。試験データは架空値で作る」 | 入力に「既存データの例」、手順に「旧版データでの移行テスト」。本人の常設指示は「現実データへの準拠を最優先」 | どちらにも決めていない。手順8は「旧版の操作で作ったデータ」または「既存データの例」と書くに留めた。実データを使うか、実データと同じ形の架空値を使うかは本人が決める。実データを使う場合、テストは端末内で行い、データをリポジトリ・外部へ出さない |
| G2 | 発動条件に「初期化・リセット・全消去機能の追加や変更」「検証失敗時の扱いの実装」を含む | 発動は「キー・構造を変えるとき」 | 依頼文に従い、発動条件から外した。初期化は手順7で、方針の入力に従う扱いにした |

| G4 | 冪等性の記載は無い（手順11に「再移行」の確認がある） | 「何度実行しても同じ結果になる作り」 | 手順4・手順8の4として加えた |
| G5 | 「既存アプリの保存キー・スキーマを指示なく変更しない」 | 記載なし | 本スキルは変更の指示を受けた後に発動するため、注意点の「してはいけないこと」に残した |

関連する既存規則: 統一指示書（`highlightyjp/app` の `docs/app-build-guide_v5.md`）§0 の 8「ユーザーデータの不可逆操作は事前にエクスポートし、版番号で固定」と、§4「スキーマ・文書構成の移行」（82〜93行。ラウンド2再評価 §4 B04 による。本清書では §4 の本文を読んでいない）。本スキルは端末内保存を対象にし、§4 は共有データを対象にする（ラウンド2再評価の記載）。規則の本文は写していない。

品質ルール:

- 根拠区分は「確認済み／評価・解釈／未確認」の3つだけを使う。テストの結果は、実行した方法と日時を書いたものだけを確認済みとする。Chromium での結果を iOS の確認済みとして書かない。
- 件数の照合は、照合した値（移行前 N 件、移行後 N 件）を書く。「問題なし」だけを書かない。
- 肯定のみの報告をしない。テストが全部通った場合も、判定不能の項目と実機未確認を書く。

してはいけないこと:

- 失敗時に無断で初期化・削除・既定値での上書きをしない。
- `localStorage.clear()` を使わない。
- `{...DEF, ...JSON.parse(saved)}` の浅いマージだけで移行済みとしない（入れ子の欠落・型の不一致が残る）。
- 新版でキー名だけ変えて旧データを放置しない（利用者には「データが消えた」状態に見える）。
- 既存アプリの保存キー・スキーマを指示なく変更しない。
