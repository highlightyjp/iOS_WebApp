# フェーズゲート判定と進行記録

## 目的
フェーズの前倒し・後戻り・フェーズ外作業を防ぎ、遷移の根拠を再確認可能な形で残す。

## 発動条件
- 指示に「Phase」「フェーズ」「ゲート」「次段階へ」が含まれる
- `state.json` / `phase_gates.md` / `PHASE_*.md` / `CLAUDE.md` のフェーズ規定があるディレクトリで作業する
- 作業完了後、フェーズ完了を宣言しようとしている

## 入力
| 項目 | 内容 |
|---|---|
| 正本 | 現在フェーズを示す唯一のファイル（例: `runbook/state.json` の `current_phase`） |
| ゲート条件 | 例: `runbook/phase_gates.md` |
| 規定 | 例: `00_core/CLAUDE.md`（読込順・自律範囲・人間承認事項） |
| 実行ログ | 例: `runbook/execution_log.md` |

## 出力
| 項目 | 内容 |
|---|---|
| 範囲判定 | 指示が現在フェーズ内か / フェーズ外か |
| ゲート判定表 | 条件 / 充足・未充足 / 根拠（ファイル・コミット・日付） / 人間承認要否 |
| 正本更新差分 | 全条件充足時のみ（`current_phase`、`phase_started`） |
| ログ1件 | 日付（JST明記）、判定、根拠、次アクション |
| 判断事項 | `pending_decisions` への追記内容 |

## 手順
1. 規定ファイルが定める読込順で、規定 → 正本 → ログを読む。
2. 指示が現在フェーズに属するか判定する。属さない場合は作業せず「フェーズ外」として報告する。
3. ゲート条件を1件ずつ判定し、根拠を付ける。人間承認が必要な条件（公開・送信・契約・金銭等）は、エージェント側で充足扱いにしない。
4. 全条件が充足した場合のみ正本を更新する。1件でも未充足なら据え置き、未充足条件と充足に必要な人間側の作業を報告する。
5. 実行ログへ時系列順に1件追記する。日付はタイムゾーンを明記する（例: `2026-07-08 (JST)`）。
6. 判断が必要な分岐は `pending_decisions` に記録し、当該タスクを保留して次に進む。
7. コミットメッセージにフェーズIDと判定を含める（例: `Phase C-5 不変量検証：全15遷移PASS`）。
8. フェーズ完了と同時に凍結する場合は `freeze-seal-verify` を発動する。

## 注意点（やってはいけないこと）
- 条件未達での前倒し遷移をしない。
- 完了・凍結済みフェーズの成果物を再生成・修正しない。
- 未着手フェーズの成果物を先行して作らない。
- ゲート条件を読み替え・緩和しない。
- 判断事項を代行しない（価格・販売形態・公開可否等）。
- ログに日付とタイムゾーンの混在、時系列の逆転を作らない。
- 利用規約に抵触する手段（ボット対策の回避・ブラウザ偽装等）でゲート条件を満たそうとしない。
